# 基线数据

`scripts/verify_release.py` 分两部分，这个目录服务于其中一部分：

| 部分 | 验什么 | 数据来自 |
| --- | --- | --- |
| 实时探活 | 维度在不在 | 现打的实时调用，标的写死在脚本的 `LIVE_BATCHES` 里 |
| **基线比对** | **数字对不对** | **这个目录** |

文件是 `logs/mcporter/` 里的原样拷贝，脚本按文件内「命令：」那一行反解出工具和
参数，文件名不参与解析，随便叫什么都行。

## 选基线的三条规则

**一、数据必须已经定盘。** 满足任一条即可：

- 归档命令里的 `date=` 早于抓取那天（查的是往日，与抓取时点无关）
- 抓取时点在 15:00 之后（当天收盘后）
- 抓取时点在 09:30 之前（开盘前，报告的数据日期是前一个交易日）

抓取时点落在当天交易时段内的，报告里「当日」是盘中快照，而重放是钉着日期查的
收盘值，两者本来就不相等；连带 5/20/60 日的均价、均量、振幅、累计涨跌全都会
跟着差一点。脚本会自己检查（`_captured_intraday`）并在报告里标注，但挑的时候
就该挑对。

**二、要够新，覆盖渲染层加过的字段。** 「当日」那一行的「开盘」是后加的，拿更老的
归档比会得到一堆"值变化"，其实只是旧数据没有这一维。当前这一套全部取自 2026-08-28
之后。

**三、必须晚于已知修复。** 这条最容易忘，代价也最大：基线捕获的是抓取那一刻的
行为，如果那时有个 bug，基线就把 bug 固化成了"正确答案"，以后每次跑都会把修好的
代码报成"不一致"。

实例：`kline_range` 的成交量单位在 2026-09-03 当天被修过。同一个标的同一段区间，
10:59 抓的归档是「股」，17:53 之后抓的是「手」，差整整 100 倍。第一次挑基线挑到了
01:21 和 17:07 那几份，于是 4 份里 3 份报出几十处"不一致"，而正确的恰恰是当前代码
（`成交额 / 收盘 = 股数`，除以 100 才是手数）。

所以拷进来之后先自己验一遍量级，别只看能不能解析。ETF 单价约 1 元、单日成交量在
「手」口径下是千万级；个股几十元、十万到百万手。按手算出来的成交额落在几亿到几十亿
才对，落到千亿就是单位错了。

## 当前这一套（每个工具 4 个标的）

| 文件 | 工具 | 标的 | 为什么是它 |
| --- | --- | --- | --- |
| `20260831082723_brief_SH603986_…` | brief | 4 个个股 | `date=2026-06-23` 钉在往日 |
| `20260828163109_brief_SH000001_…` | brief | 4 个指数 | 16:31 抓的；含 SH000688（没有资金流页面的那类） |
| `20260831110143_brief_SH512670_…` | brief | 4 个 ETF | `date=2026-06-15` 钉在往日；ETF 是独立代码路径 |
| `20260828083036_full_SH600362_…` | full | 4 个个股 | 次日 08:30 抓的，数据日期是前一交易日；带 `fund_flow_limit=60` |
| `20260828200112_kline_daily_SH600362.md` 等 **4 份** | kline_daily | SH600362 / SH600489 / SH601138 / SH601899 | 20:01 抓的，与上面那份 full 同一批标的 |
| `20260903174457_kline_range_SH600118.md` 等 **4 份** | kline_range | SH600118 / SH600362（个股）<br>SZ159995 / SH588000（ETF） | 全部取自 09-03 17:44 之后，也就是成交量单位修复之后 |
| `20260903183039_market_events_date-2026-08-24_…` | market_events | `sources=limit_up` 的整个事件池 | 18:30 抓的，`date=2026-08-24` |
| `20260828163113_market_breadth_.md` | market_breadth | —— | 16:31 抓的。没有日期参数，天然不可重放，留着只当形状参考 |

kline_daily 和 kline_range 的 4 个标的是拆成 4 份归档的：这两个工具在生产上从来
只带一个 `symbol=`，硬凑一个多标的调用会去比一条线上不会走的路。

## 还缺的

| 缺什么 | 为什么 |
| --- | --- |
| medium | 整个归档库只有一份，抓于 2026-06-15 盘中 10:35，违反规则一 |
| tech | 归档库里那两份都被截断了（JSON 没闭合），脚本会跳过并说明 |
| kline_range 的指数与北交所 | 修复之后（09-03 17:00 起）的窗口里没有指数归档；BJ920021 有一份，但内容是"未找到数据"，等于把一次失败固化成基线 |

都在能通东财的机器上补：

```bash
python scripts/verify_release.py --only medium,tech --capture
```

`--capture` 只在探活一处维度都不缺时才写文件——拿一份不完整的输出当下次的账本，
只会把当前的故障固化成"正常"，也就是规则三说的那件事。所以补基线要在数据源健康的
机器上做。
